## 1. 决定及原始依据

采用单屏、固定分区、任务直接展开的作战台。其目的在于降低多个项目同时推进时的巡视、上下文切换和人工决策成本；不是再增加一个需要逐层点开的管理后台。

管理对象限于 yttt 管理的项目、Agent 与其派生执行，不是全机器进程监控。

此前三个备选布局被否决的主要原因是：具体任务被压成摘要，理解任务、查看执行关系和处理问题仍需要点击展开或切换视角。后续不再沿着三个独立页面的方向扩展。

## 2. 固定的页面结构

| 区域 | 已确认的职责与形式 |
| --- | --- |
| 紧凑顶栏 | 品牌、工作范围和少量全局状态；不使用大标题、说明区或大型统计卡挤占任务空间。 |
| 上部任务矩阵 | 多个项目或目标分区同时可见；每个分区默认展开多条任务。任务是主体，Agent 是任务的执行属性。 |
| 任务行 | 直接显示任务名称、状态、执行者及时间等必要信息；不以“派生几个”或完成比例代替具体工作。 |
| 左下待回答区 | 集中展示问题、必要上下文和可选回答；主要回答在原位完成。 |
| 中下关联对话区 | 显示所选任务的完整名称、身份、上下文和关联对话；提供绑定当前目标的补充输入和必要操作。 |
| 右下执行队列 | 展示主 Agent 与派生执行的任务归属、状态和持续时间；选择后与任务矩阵、关联对话联动。 |
| 底部状态栏 | 简短显示操作反馈、快捷键提示与原型数据性质，不弹窗遮挡全局。 |

视觉基线为当前原型的深色、细边框、高密度任务行、列对齐与状态明暗层级。布局的主次关系和固定区域得到确认；原生主题适配、字体度量与不同窗口尺寸下的精确像素值不在本次冻结范围。

原型参考比例：上部矩阵与下部处理区为 `1.72:1`；下部左、中、右为 `1.38:1.12:0.78`。这是实现对照值，不要求在不同屏幕尺寸上机械保持每一个像素。

## 3. 固定的交互原则

1. **先直接看见，再选择处理。** 日常了解项目主要任务、阻塞、失败及待回答事项，不要求打开详情。
2. **单屏联动，不跳页。** 选择任务或执行记录，只更新同屏关联上下文和高亮；其他项目仍可见。不把页签切换或详情弹窗作为常规流程。
3. **稳定位置。** 更新、选中、回答和状态变化不自动重排项目；不自动轮播或翻页。
4. **问题原位处理。** 选项可直接回答；需要自由输入时，使用同屏关联对话区。回答后保留原位反馈，不把用户立即带去另一个项目，也不推动其他问题的位置。
5. **明确输入归属。** 展示当前回复绑定的项目、任务或问题；切换选择不串用草稿，不把一个问题的答案提交给另一个执行。
6. **保留过程。** 已结束任务弱化但保留；回答与失败留下可查记录。归档策略和保留时长后续确定，不承诺无限保留。
7. **运维不遮挡全局。** 需要处理异常时，在固定关联区域呈现适用的操作和结果。是否支持某个真实动作，由后续实现与 provider 能力决定，不能伪造按钮能力。
8. **局部溢出。** 超出区域容量的内容在相应区域内查看，不把整个作战台替换成另一页。超大项目规模下的分组、容量与密度策略仍需讨论。

## 4. 固定的显示语义

- 等人回答与等工具、子任务、构建或其他依赖分别展示；不是所有等待都进入人的待处理队列。
- 连接失联或缺少观测不等于执行失败。保留最后已知任务和未回答问题，明确标记当前未知。
- 失联时不能将回答显示为已成功提交；恢复连接不意味着重新启动执行或自动回答问题。
- Agent 轮次结束、任务执行结束与人工验收分开表达。
- 完成条目和状态块要有可说明的口径；不能由工具活动或运行时长推导虚假的完成百分比。
- 任务、提问、对话与执行队列之间的关联要能支撑准确定位，不依赖用户自己记忆或猜测。
- 状态同时使用文字、符号和颜色，不能只靠颜色区分。

这些是用户可见语义与安全要求，不是对数据库表、事件协议或 provider 接口的提前选型。

## 5. 原型已验证的范围

本节记录原型阶段已经实际执行的浏览器检查，不代表正式应用已经具备这些能力。

- 在 `1568×1073` 和 `1920×1080` 视口，默认演示场景的九个项目、54 条任务、三个问题和 16 条执行记录均可直接看见，无需滚动。
- 选择任务不导航、不打开弹窗，关联对话正确联动。
- 点选回答更新对应任务和依赖，保留回答记录，项目及问题的位置不变。
- 自由回答绑定正确问题；草稿随目标保存；输入框方向键不改变所选任务；支持 Ctrl/Command + Enter 提交。
- 拒绝授权不会启动依赖该权限的工作。
- 失联保留业务状态和问题、禁用回答；模拟恢复不改变执行编号，也不自动回答。
- 模拟重试保留前次失败并产生新的执行编号；人工验收单独记录并更新任务完成数。
- 集中提问场景只在待回答区域内滚动；直接以文件方式打开原型可运行。

所有上述操作均为本页内存模拟，无真实 Agent、网络控制、文件写入或生产凭据访问。

## 6. 明确未冻结的事项

- 演示中的项目数、任务数、Agent 数、状态时长、文案、模型名称和具体任务内容。
- 三列三行矩阵是否作为所有屏幕和项目规模下的固定数量上限；原型数量不构成产品容量限制。
- 项目、目标、任务、轮次、执行和提问的正式数据模型及身份关联。
- 目标与阶段来自人工建立、Agent 结构化上报、对话整理，或哪种组合。
- 每一种 provider 实际可用的观测点、提问选项、回复通路与运维能力。
- Host 聚合、跨窗口去重、实时刷新、时序、历史存储、保留策略及权限实现。
- 对话区读取完整 transcript、片段、摘要还是结构化记录，以及其权限和隐私处理。
- 实际失败、中断、恢复、重试、授权、验收的协议和结果确认方式。
- yttt 原生界面的入口、窗口组织和 GPUI 实现方案。
- 费用、token、资源指标、预计完成时间等附加数据是否纳入。
- 原型的场景选择、重置按钮和“演示数据”标记是否出现在正式功能中；它们不是已确认的生产功能。

## 7. 后续讨论顺序与变更边界

后续先讨论“项目—目标/任务—执行—提问”的归属与身份，再逐项对齐数据来源和已有观测，随后讨论同屏回复与运维操作的真实控制能力，最后确定正式实现方案。

讨论实现时，以本文件及 `1531549` 的截图为页面基线。数据缺口不能静默通过隐藏任务、改回逐级详情或拆成多页来解决；需要改变已确认的信息组织或主要交互时，应回到用户确认。

本次不启动正式实现，也不把原型提升为原生应用功能。

## 8. 重开设计样本

原型页面可直接打开，也可在包含批准原型的工作树根目录运行：

```sh
python3 -m http.server 4178 --bind 127.0.0.1 --directory crates/yttt-ui/prototypes/command-center
```

然后打开 `http://127.0.0.1:4178/`。如该端口已有上一轮预览服务，可继续使用，不重复启动。

运行入口、截图和原型提交是持久设计依据；某一次预览服务是否仍在运行，不影响本次页面批准结论。
